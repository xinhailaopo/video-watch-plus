# 与 browser-skill 配合：看现场 + 做取证

本技能不是孤立使用的。它与
[`@wxg-prc-cpg/browser-skill-dsh-plugin`](https://www.npmjs.com/package/@wxg-prc-cpg/browser-skill-dsh-plugin)
（底层是腾讯开源的 [BrowserSkill](https://github.com/Tencent/BrowserSkill)）配合时，
覆盖的场景会完整得多 —— 一个负责**看现场**，一个负责**做取证**。

---

## 两条路各自拿到什么

| | **browser-skill**（实时浏览器） | **video-watch-plus**（落盘分析） |
|---|---|---|
| 需要下载 | ❌ 不需要 | ✅ 需要 |
| 取帧 | 只能按工具调用节奏采样，间隔不匀 | **任意时刻精确取帧**、逐帧量测 |
| 声音 | ❌ **拿不到**（截图采不到音频） | ✅ ASR 转写 + 声学侦察 |
| 读小字 | 受截图分辨率限制 | 可裁切放大（唯一可信的读字通道） |
| **独有能力** | **弹幕 / 标签 / 评论 / 相关推荐 / 登录态 / 播放暂停拖拽** | 可复现、可核算的取证交付 |
| 适合 | 看个大概、需要交互或登录的内容 | 精确取证、读小字、转写语音 |

---

## 为什么配合起来更强：一个实测例子

对同一个 B 站视频，两条路各跑一遍，结论的完整度差异很大。

**落盘路（本技能）给到的**：帧精确量测（545 帧、切点 0.07/1.07/1.41/10.11s）、
烧录字幕的全文读取并**纠正了 ASR 的 3 处同音错字**、6 段带时间戳的转写。

**实时路（browser-skill）补齐的三件事**，是落盘路结构上拿不到的：

1. **页面标签**：`搞笑 / AI / claude / deepseek娘 / 蓝色大肥鱼 / 蓝色`，
   外加"含AI生成内容"标记 —— 这直接把画面里"蓝发→橙发"的变身指向了具体对象，
   而单看画面只能推断"可能是在指代某两个品牌色"。
2. **弹幕**：`坏了，检测到国区用户了` —— 这一句把整支视频的笑点说破了。
   画面和音轨都只说了"角色化作星点消失"，**为什么消失**只存在于弹幕里。
3. **相关推荐**：确认这是一个成套的梗系列，而不是孤立作品。

换句话说：

> **落盘路回答"发生了什么"；实时路回答"这件事在什么语境里"。**

两个都缺，结论就会偏 —— 落盘路容易把梗当事实，实时路容易只看到表面。

## 推荐的工作流

```
第一步（要不要看）      browser-skill 打开链接
                         ↓ 看标签/弹幕/简介，判断这个素材值不值得深挖
第二步（怎么取证）      yt-dlp 落盘（如果值得）
                         ↓
第三步（量测）          vw.py probe        → 切点/冻结/静音/运动曲线
                         ↓
第四步（读画面）        vw.py grid → 我看图版 → 需要文字就裁切放大
                         ↓
第五步（听声音）        audio_probe.py     → 先判有没有人声
                         ↓
第六步（转写）          asr_hallucination_check.py → 再转写并证伪幻觉
                         ↓
第七步（互校）          三路对齐；文字冲突以画面为准（见 verification.md）
                         ↓
第八步（补语境）        回到 browser-skill 看弹幕/评论，补齐"为什么"
```

## browser-skill 的启用前提（避免踩空）

它不是装上就能用，链路是 **`bsk` CLI + 本地 daemon + 浏览器扩展 + dsh 插件**四件套。
实测踩过的点，按顺序检查：

| 现象 | 根因 | 处理 |
|---|---|---|
| `the bsk CLI ("bsk") was not found` | CLI 没装或不在宿主 PATH 上 | 装 `bsk`，并确保它在**启动 dsh 时使用的那个 PATH** 上；或把二进制放到一个已在 PATH 上的可写目录 |
| `cannot start an independent Windows daemon ... os error 5` | daemon 无法从沙箱进程树分离 | 用持久后台任务跑 `bsk daemon start --foreground`；**dsh 宿主自己也起不来**，这一步没有捷径 |
| daemon 跑一会儿自己没了 | 默认 **10 分钟空闲即退出** | 用 `--daemon-idle 24h` 之类的参数拉长 |
| `0 browsers connected` | 浏览器**根本没开**（不是扩展的问题） | 先确认浏览器进程在运行，再看扩展弹窗的连接开关与端口 |
| 换台机器又要重来 | 上述四件套每台机器都要配一次 | 建议**让 agent 代做**（见下节） |

## 为什么这两类插件最好由 agent 来装

本技能与 browser-skill 都属于「装了要用起来才算数」的类型，而它们的安装路径上有一堆
**只有踩过才会知道**的细节：PATH 究竟是谁的 PATH、daemon 能不能分离、端口对不对、
模型从哪个源下、`av` 的版本区间是多少……

这些细节靠人读文档一处处试，成本远高于让 agent 直接做，原因有三：

1. **agent 能读源码验证，而不是猜**。本仓库对上游两处 Windows 缺陷的定位，就是靠读
   `paths.ts` / `escape_filter_path()` 的源码 + 写对照实验测出来的，不是靠搜索。
2. **agent 能在失败处继续挖**。例如"TCP 不通但 HTTP 通"这种矛盾，人容易归因为
   "网络问题"就停手；agent 会去查 WinINET 与 WinHTTP 的差异，最后定位到
   git 不走系统代理。
3. **agent 能把过程固化成可复现的脚本**。本仓库的 `scripts/setup-windows.ps1`
   就是这么来的：先手工跑通，再把每一步的校验（7 个必需滤镜、libfreetype、IM 子命令探测）
   写进脚本。

**所以推荐做法是**：把仓库目录交给 agent，说一句

> 「按 SKILL.md 把环境装好，装完跑 `vendor/vw.py doctor` 和 `scripts/build_testclip.py` 验收，
> 把踩到的坑补进 references/」

让 agent 去装、去撞、去记录。人只需要在**必须由人做**的地方动手 ——
比如浏览器扩展的安装与授权（这一步上游明确要求用户本人完成）。
